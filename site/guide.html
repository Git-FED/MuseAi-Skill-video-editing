A short, practical route from repository to installed skill. The packages are intentionally plain: inspect the instructions, verify the requirements, then hand over only what you mean to use.

01 / INSTALLATION

From clone to custom skill.

These commands clone the umbrella repository, check the recorded package hashes, and copy one skill into a workspace folder. Choose a different skill folder name if you need another tool.

CLONE / VERIFY / COPY
git clone https://github.com/Git-FED/fed-os-muse-skills.git
cd fed-os-muse-skills
make verify
mkdir -p ~/workspace/custom-skills
cp -r skills/muse-footer-layout ~/workspace/custom-skills/
i

Before you run it: check the skill’s prerequisites and read SKILL.md. The install example uses muse-footer-layout; you can copy any folder under skills/.

02 / SHARED PACKAGE CONTRACT

Same shape. Easier to inspect.

Each skill is designed to be read as a small, self-contained package. The contract makes it clear which files explain the behavior, requirements, safety, and release history.

SKILL PACKAGE / EXPECTED SHAPE01 FOLDER
muse-skill-name/
├── SKILL.md          the playbook the agent follows
├── manifest.json     identity, requirements, file hashes
├── README.md         human-facing setup and usage
├── LICENSE           MIT terms
├── SECURITY.md       how to report a vulnerability
├── CHANGELOG.md      version notes
├── references/       optional lookup data
└── scripts/          optional deterministic helpers

If a file isn’t load-bearing—if no one can say what would break when it disappears—it probably doesn’t belong.

03 / SHARED RULES

Six rules that keep it honest.

01

No HTML in skill repos

A skill’s output is a plan or decision, not markup pretending to be an executable package.

02

No live credentials

Client IDs, keys, OAuth state, checkout IDs, and tokens stay out of tracked files and URLs.

03

Canonical links only

Use stable provider handles and landing pages—not session-bound or live checkout URLs.

04

Disclose referrals

When a link may earn a credit, put a plain-language disclosure beside it.

05

No fake gates

A client-only age checkbox is not verification. Don’t claim a gate the system does not enforce.

06

Verify recorded hashes

make verify checks file consistency with each skill’s manifest. It does not prove publisher identity.

04 / QUICK ANSWERS

Before you dive in.

Do I need a build step or package manager?

No. The public site and the skill packages are intentionally static. Clone the repository and use the included instructions and scripts.

Do the packages include live credentials?

No. The repository rule is to keep live credentials out. A requirement can name an environment variable, but tracked files should not contain its value.

Does hash verification prove who published a package?

No. make verify checks consistency between files and their recorded hashes. It is a useful integrity check, not an identity signature.

What if a check fails or a prerequisite is missing?

Stop and surface the specific failure. The skills are designed to prefer an explicit failure over silently switching tools or inventing a successful result.
